# Performance

wildcsv does more per byte than `encoding/csv`: it validates UTF-8, enforces limits on every field and record, and keeps the line and column of every field. This page measures what reading costs, how it scales with goroutines, and where wildcsv is still slower.

All figures: windows/amd64, Go 1.27.3, Intel Core i9-9900K (8 cores, 16 threads), the median of three runs. The inputs are generated by the benchmarks themselves, so anyone can reproduce them:

- **plain**: unquoted ASCII fields: numbers, identifiers, dates, decimals;
- **quoted**: quoted fields with commas, line breaks and doubled quotes;
- **multibyte**: unquoted fields of Spanish, Portuguese, German and Japanese text.

## How wildcsv reads

- **Eight bytes at a time.** A record that lies wholly in the read buffer is scanned a word at a time: each word is loaded once, every delimiter in it ends a field, and the first quote or line break ends the run. Long quoted fields are crossed with `bytes.IndexByte`. UTF-8 is validated once per record, and only when a byte of 0x80 or above was seen. Anything unusual (a stray quote, invalid UTF-8, a record near a limit) is left to the general path, which defines every result.
- **One copy per record.** Fields are offsets into the buffer; a record becomes one string that its fields share, and doubled quotes are made single in place. `ReadSlices` skips even that copy.
- **In parallel.** By default, once an input passes 128 KiB, the rest is cut into chunks of about 128 KiB at line feeds where the quotes balance, read by up to 8 goroutines, and returned in order, with the same records, errors, warnings and positions as one goroutine. [design.md §8.6](design.md#86-speed-and-concurrency) describes how a wrong cut is detected and read again.

## Reading

`BenchmarkRead` reads each input repeated to 32 MiB, with the dialect given so that only reading is measured, and with `ReuseRecord` set for both libraries:

```sh
go test -run '^$' -bench 'BenchmarkRead$' -benchtime 8x -count 3 .
```

Throughput, and the speed against `encoding/csv`:

| Input | `encoding/csv` | wildcsv `Read` | wildcsv `ReadSlices` | wildcsv `Read`, 1 goroutine | wildcsv `ReadSlices`, 1 goroutine |
| --- | ---: | ---: | ---: | ---: | ---: |
| plain | 390 MB/s | 1,959 MB/s (5.0×) | 2,119 MB/s (5.4×) | 435 MB/s (1.12×) | 543 MB/s (1.39×) |
| quoted | 340 MB/s | 1,352 MB/s (4.0×) | 1,493 MB/s (4.4×) | 334 MB/s (0.98×) | 388 MB/s (1.14×) |
| multibyte | 445 MB/s | 1,479 MB/s (3.3×) | 1,938 MB/s (4.4×) | 357 MB/s (0.80×) | 405 MB/s (0.91×) |

The default columns use `Options.Concurrency` 0; the last two set it to 1.

Allocations: `Read` allocates one string per record, as `encoding/csv` does. `ReadSlices` with one goroutine allocates nothing per record: 29 allocations in all for 32 MiB, those of opening the reader.

## Scaling with goroutines

`BenchmarkReadConcurrency` reads the same 32 MiB inputs through `Read` with a fixed `Options.Concurrency`:

| Input | 1 | 2 | 4 | 8 | 16 |
| --- | ---: | ---: | ---: | ---: | ---: |
| plain | 444 MB/s | 763 MB/s | 1,462 MB/s | 2,086 MB/s | 2,310 MB/s |
| quoted | 346 MB/s | 476 MB/s | 1,085 MB/s | 1,149 MB/s | 1,271 MB/s |
| multibyte | 363 MB/s | 661 MB/s | 1,331 MB/s | 1,612 MB/s | 1,641 MB/s |

Past the physical cores the gains are small: one goroutine reads the source and cuts it, another returns the records, and memory bandwidth is shared. The default stops at 8.

## Small inputs

The default hands over to goroutines after 128 KiB, where measurement showed parallel reading start to pay. Below that, wildcsv reads in the calling goroutine. Throughput of the default against `encoding/csv` by input size, through `Read`:

| Input | 128 KiB | 512 KiB | 1 MiB | 4 MiB |
| --- | ---: | ---: | ---: | ---: |
| plain, `encoding/csv` | 403 MB/s | 407 MB/s | 413 MB/s | 375 MB/s |
| plain, wildcsv | 426 MB/s | 457 MB/s | 566 MB/s | 1,208 MB/s |
| multibyte, `encoding/csv` | 480 MB/s | 463 MB/s | 480 MB/s | 459 MB/s |
| multibyte, wildcsv | 349 MB/s | 466 MB/s | 626 MB/s | 1,214 MB/s |

Opening a reader whose dialect is declared costs about 33 µs; the header guess and the column kinds are worked out only if `Detection` is called.

## Where wildcsv is slower

- **One goroutine, text full of multi-byte characters**: 20% slower through `Read`. Every record that holds a byte of 0x80 or above is validated as UTF-8, which `encoding/csv` does not do at all: it can return invalid UTF-8. In the multibyte input every record does, and validation takes about a quarter of wildcsv's time on it. A branch-free automaton was tried in place of the standard library's `utf8.Valid`; without the BMI2 instructions, which Go does not use by default, it was only about 15% faster on these records, so it was not kept.
- **Inputs under 128 KiB of such text**: the same cost, since they are read in one goroutine; at 128 KiB the default is 27% slower than `encoding/csv`.

If you read trusted UTF-8 files of a few hundred kilobytes, whose dialect you know, `encoding/csv` is as fast or faster and is part of the standard library.

## Memory

A reader in one goroutine holds a 64 KiB read buffer, a 32 KiB decode buffer when the input is not UTF-8, and the current record, which `MaxRecordBytes` bounds. A parallel reader holds besides a few chunks of up to 160 KiB of text per goroutine, each with its records as `Read` or `ReadSlices` will hand them out. Reading the 32 MiB plain input through `ReadSlices`, the heap in use peaked 10 to 15 MiB above its starting point with 2 to 8 goroutines, garbage not yet collected included. Through `Read` the peak is that of the strings returned, as with one goroutine or `encoding/csv`.

## Detection

`BenchmarkDetect` runs `Detect` with default options on the 8 MiB inputs, which examines their first 64 KiB, and on a sample built to produce many candidate dialects (five delimiters on every line):

```sh
go test -run '^$' -bench 'BenchmarkDetect' -benchtime 8x -count 3 .
```

| Input | Median time |
| --- | ---: |
| plain | 0.18 ms |
| quoted | 0.65 ms |
| multibyte | 0.39 ms |
| many candidates | 3.02 ms |

On the 421 file runs of the development half of the accuracy benchmark ([accuracy.md](accuracy.md)), the 95th percentile of `Detect` was 3.9 ms and the slowest file took 9.6 ms, including opening the file.
